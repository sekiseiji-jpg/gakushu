# 学習アプリ群 開発で得た知見

最終更新: 2026-10-22

日本史1本から始めて、社会5分野・理科4分野・数学3分野・国語4分野・英語3分野（計19分野）へ横展開し、ポータルと3階層の検索でまとめるまでにぶつかった問題と対処のまとめ。
各項目は「症状 → 原因 → 対処」の順。日本史単独のときの知見は `日本史/知見.md` にもある。

## 1. 1つのエンジンを複数分野で使い回す

### 1.1 2つ目を作るときに「コピーして書き換える」とすぐ破綻する
- **状況**: 日本史のコードをコピーして世界史を作ると、同じバグを2か所で直すことになる。4分野なら4か所。
- **対処**: 画面の動作（`app.js`）は1本にし、分野ごとの違いを `data-units.js` 冒頭の `APP` オブジェクトに全部追い出した。雛形から各フォルダへ生成するスクリプトを用意し、**雛形を直して再生成**する運用にした。
- **効果**: 「出題形式の呼び名を変える」「ヘッダーに戻るリンクを足す」といった変更が、雛形1か所の修正＋再生成で4分野に反映できるようになった。

### 1.2 ハードコードされた日本語は、横展開の瞬間に牙をむく
- **症状**: 地理アプリでクイズの「出題開始」を押しても何も起こらない。
- **原因**: `app.js` に `const CATS = ['政治','外交','社会経済','文化'];` と直書きされていた。地理の分野は「自然・産業・人口・都市・地誌」なので、絞り込み条件に一致する問題が0件になり、`startQuiz()` が早期 return していた。
- **対処**: `APP.cats` から読むように変更。同様に「時代」「年表」「史料」「年代配列」といった語も、すべて `APP.unitWord` / `APP.listWord` / `APP.typeLabels` に外出しした。
- **教訓**: 横展開するなら「この文字列は分野によって変わるか？」を1つずつ確かめる。**無言で0件になる**類のバグは、エラーが出ないぶん発見が遅れる。

### 1.3 同じ形式名でも、分野によって意味が変わる
- 歴史の `ord` は「年代配列」だが、地理では「順位配列（生産量の多い順）」になる。`src` も歴史は「史料」、地理は「資料読取（統計表）」、政経は「資料・条文」。
- データ構造は同じでよいが、**画面に出す呼び名は分野ごとに変える**必要があった。`APP.typeLabels` で解決。

## 2. データ作成

### 2.1 長い日本語を書くと、別言語の単語が混入する（再発4回）
- **症状**: 本文中に `village`、`private`、`market`、`social`、`água`、`большой` といった別言語の語が紛れこむ。見た目では気づきにくい。
- **対処**: 書き終えるたびに機械的に検査する。ただし**ファイル全体を grep してはいけない**（次項）。
- **教訓**: 1回の事故ではなく、長文を大量に書けば必ず起こる現象として扱う。チェックを工程に組みこむ。

### 2.2 言語チェックは grep ではなく Node で「本文フィールドだけ」を見る
- **失敗**: `grep -nP '[a-zA-Z]{3,}'` で探したところ、①macOS 標準の BSD grep には `-P` がなくスクリプトから呼ぶとエラー ②`id:'q-heian-9'` や `type:'sel'` などコード部分が大量に引っかかり、本物の混入が埋もれる（378件中、本物は2件）。
- **対処**: データを Node で `require()` し、`q` / `src` / `exp` / `choices` という**本文フィールドだけ**を取り出して正規表現をかける小さなスクリプトにした。`GHQ`・`GDP`・`Cfa`（気候区分）・`SNS` など正当な欧字は許可リストに入れる。誤検出がゼロになり、本物だけが出るようになった。
- **教訓**: 構造化データは構造を使って検査する。検査対象を「ファイル全体のテキスト」から「意味のあるフィールド」に絞ると、ノイズが消えて検査が実用になる。

### 2.3 検証スクリプトを先に作ってから書き始める
- 4分野×180問前後を書くにあたり、先に1本の検証スクリプトを用意した。件数・単元別内訳・id重複・正解インデックスの範囲・選択肢数・形式別件数・言語チェックを1コマンドで確認できる。
- データファイルは末尾の `];` と `module.exports` を一時的に外しておき、検証時だけ連結して読ませる方式にした。3〜4単元ずつ追記しては検証、をくりかえせる。

### 2.4 形式のカバー率は単元ごとにクロス集計する
- 全体の形式別件数だけ見ていると、「特定の単元に年代配列が1問もない」といった偏りに気づけない。単元×形式の表を出すようにしたら、実際に穴が見つかった。
- なお日本史の旧石器・縄文時代だけは史料問題を置いていない。文字史料のない時代であり、史料読解の設問が成り立たないため。**「全単元で形式をそろえる」という機械的な目標より、内容として成立するかを優先する。**

### 2.5 統計データは「年次」と「おおよその順位」で書く
- 地理の統計は年によって順位が入れ替わる。細かい数値を載せると古くなるのが早い。
- 「2022年ごろ」のように年次を明記し、上位3〜5か国の**顔ぶれと順序の傾向**を書くようにした。入試で問われるのもその水準である。

### 2.6 `cmb`（組合せ）は、選択肢の形が作問を縛る
- 選択肢は `['a・c','a・d','b・c','b・d']` に固定されている。つまり**正しい文は {a,b} から1つ、{c,d} から1つ**でなければならない。
- これを忘れて a と b の両方を正しくした問題を、数学だけで8問作ってしまった。どの選択肢にも当てはまらないので、正解が存在しない。
- 画面上は何事もなく表示され、解いてみるまで気づかない。**検証スクリプトで `q.choices[q.a]` が `/^[ab]・[cd]$/` に一致するかを機械的に確認する。**

### 2.7 解説に書いた番号と `a` がずれる
- 解説に「正解は①」と書いておきながら `a:2`（＝③）になっている、という食い違いが `ord` で6問発生した。
- 人間が読むと矛盾しているが、プログラムは何も言わない。**解説から「正解は①」「①が正しい」を正規表現で抜き出し、`a` と突き合わせる検査**を入れて全件つぶした。

### 2.8 シャッフルしない形式は、正解位置の偏りがそのまま出る
- **`cmb` と `ord` はシャッフルしない**ので、作ったときの偏りが学習者にそのまま届く。`sel` と `src` は出題時にシャッフルされるので既定では見えないが、**設定でシャッフルを切るとそのまま出る**（8.6 で後から均した）。
- 実際、`cmb` の正解が①に53%集中していた回がある。「最初の選択肢を選べば当たる」という攻略法が成立してしまう。
- 形式ごとに正解インデックスを集計し、**最大でも5割を超えたらエラー**にした（`chk.js`）。細かいしきい値は `bias.js` が全4形式について見る（`sel`・`src`・`cmb` 35%／`ord` 30%）。
- 偏ったときは作り直さなくてよい。**文 c と文 d を入れ替えれば、正解が a・c → a・d にずれる。** 解説中の番号と c/d の言及も一緒に入れ替えるスクリプトを書けば、機械的に分散できる。

### 2.9 数式は記号で書かず、日本語の言葉で書く
- 数学では「2乗」「平方根」「導関数」「底」のように日本語で書き切ることにした。
- 理由は3つ。記号は端末やフォントで表示が崩れる、読み上げが成立しない、そして**ラテン文字の混入チェックに引っかかって本当の誤りが埋もれる**。
- 言葉で書くと説明がやや長くなるが、「なぜそうなるか」を書く本アプリの方針とはむしろ相性がよかった。

## 3. 見た目と UI

### 3.1 ダークモードで「ブランド色の上の白文字」が読めなくなる
- **原因**: `--primary` を「アクセント色」と「背景色」の両方に使い回していた。ダークで明るい色に反転させると、その上の白文字のコントラストが落ちる。
- **対処**: ①ダークでは `--primary-text` を暗い色にする ②ヘッダーだけは別変数 `--header-bg` / `--header-fg` を用意し、明暗どちらでも「濃い色＋白」で固定する。**背景として使う色と、文字・線として使う色は変数を分ける。**

### 3.2 ダークの指定は2か所に書く
- 設定で明暗を強制切替できるようにすると、`@media (prefers-color-scheme: dark)` だけでは足りない。`:root:not([data-theme="light"])` 付きのメディアクエリ版と、`:root[data-theme="dark"]` の直接指定版の**両方**が要る。片方を忘れると、設定でダークにしたときだけ色が古いままになる。

### 3.3 `color-mix()` にはフォールバックを
- 単元色からグラデーションを作るのに `color-mix(in srgb, var(--ec) 60%, #000)` を使った。未対応ブラウザでは宣言ごと無視されて背景が透明になり、白背景に白文字で消える。直前に `background: var(--ec);` を書いて上書きさせる。

### 3.4 分野ごとに配色とフォントを変えると、取り違えが減る
- 日本史は臙脂＋明朝、世界史は紺＋明朝、地理は緑＋ゴシック、政経は紫＋ゴシック。
- 見た目で「いま何をやっているか」が分かるので、ポータルから入ったときの迷いが減る。機能が同じアプリを並べるときは、**意図的に差をつける**ほうがよい。

## 4. フォルダ構成とポータル

### 4.1 ポート番号は必ず先に空きを確認する
- **症状**: ポータルを8770で起動したら、`/` は200を返すのに `/社会/` が404。
- **原因**: 別アプリ（六法全書）がすでに8770を使っていた。自分のサーバーは起動に失敗し、既存サーバーのページが返っていた。theme-color が自分の指定と違うことで気づいた。
- **対処**: `lsof -nP -iTCP:<port> -sTCP:LISTEN` で確認してから割り当てる。既存のサーバーは**止めない**（他の作業を壊す）。
- **教訓**: 「200が返る」はサーバーが正しいことを意味しない。**返ってきた中身**を確認する。

### 4.2 フォルダ名に「・」を使っても動く
- `政治・経済` のようにフォルダ名に中黒を使っても、ブラウザは自動で URL エンコードするため問題なく動く。
- ただし `curl` でテストするとき、`urllib.parse.quote()` の既定は `/` もエンコードしてしまうので `safe='/'` が要る。テスト側のミスを実装のバグと誤認しかけた。

### 4.3 Service Worker はディレクトリごとにスコープが分かれる
- ポータル（`/sw.js`）と各アプリ（`/社会/<分野>/sw.js`）がそれぞれ Service Worker をもつ。より深い（具体的な）スコープの登録が優先されるため、衝突しない。
- ポータル側のキャッシュ一覧にはアプリのファイルを含めない。各アプリが自分で面倒を見る。

### 4.4 生成スクリプトの出力先は、フォルダを動かしたら必ず直す
- **症状**: フォルダを `学習アプリ/社会/` 配下へ移したあと、雛形に「戻るリンク」を足して再生成したのに、アプリに反映されなかった。
- **原因**: 生成スクリプトの出力先が移動前のパス（`TOOL/<分野>`）のままで、**そこに空のフォルダを作り直していた**。本物のアプリには何も書かれていない。エラーは出ず、スクリプトは「生成しました」と正常終了していた。
- **気づいた経緯**: ブラウザで `document.querySelector('.home-btn')` が `null` を返したので、ファイルを直接 `grep` したら本物側に入っていなかった。
- **対処**: 出力先を新しいパスに直して再生成し、誤って作られたフォルダを削除した（データファイルの有無で本物と区別できるようにして確認した）。
- **教訓**: 生成系のスクリプトは「どこに書いたか」を必ず出力させ、**作業後にその出力を読む**。パスを持つスクリプトは、ファイルを動かした時点で壊れていると考える。

### 4.5 各アプリに「戻る」導線を用意する
- ポータルから入ったのに、アプリ内から戻る手段がないと行き止まりになる。ヘッダー左に `◀`（分野一覧へ）を置いた。
- 雛形に入れて再生成したので、4分野すべてに一度で反映できた（1.1 の効果）。

## 5. 動作確認

### 5.1 スクリーンショットは1手遅れて見えることがある
- **症状**: ブラウザ操作 → 即スクリーンショット、で「クリックが効いていない」「画面が真っ白」に見えた。
- **実際**: DOM を調べると処理は完了していた。パネルのフェードイン（`animation: fade .22s`）の途中が写っていただけ。
- **対処**: 「効いていない」と判断する前に DOM を直接確認する（`document.getElementById(...).innerHTML` など）。見た目を確かめたいときは1〜2秒待ってから撮る。

### 5.2 全件を機械的に回して確認する
- 各アプリで「15単元 × 6サブタブを開く」「全180問を表示して正解を選び、採点結果を確認する」をブラウザのコンソールから一括実行した。手でクリックして辿るより確実で速い。
- `app.js` を素のスクリプト（モジュールではない）にしているので、`openEra('kikou','detail')` や `startQuiz()` をコンソールから直接呼べる。これがテストを容易にしている。

### 5.3 ブラウザのキャッシュで「直したのに変わらない」
- `?v=` を上げずに `app.js` を差し替えても、ブラウザが古いものを使い続ける。実際に `CATS` の修正が反映されず、原因を探して時間を使った。
- **ファイルを変えたら必ず `?v=` と `CACHE` を上げる。** ローカル確認のときも例外にしない。

## 6. 運用

### 6.1 localStorage のキーは分野ごとに分ける
- `nihonshi.v1` / `sekaishi.v1` / `chiri.v1` / `seikei.v1`。同じ仕組みでも学習記録は混ざらない。
- 各キーの中身は1つのオブジェクトにまとめ、`load()` で既定値とマージする。あとから項目を足しても既存ユーザーが壊れない（実際、開発中に「学習した日数」用の `days` を後から追加したが何もせずに動いた）。

### 6.2 外部 CDN を使わない
- 外部 API もフォントの CDN も使っていないので、Service Worker に列挙したファイルだけで完全に動く。学習アプリは回線のない場所で使われるため、この制約は最初から守るほうが楽。

## 7. 理科を足して分かったこと（2026-10-19 追記）

### 7.1 「APP に出す」つもりでも、雛形HTMLに直書きが残る
- 共通エンジンの設計目標は「分野を増やすとき `app.js` を触らない」ことだった。ところが理科を生成したら、タブに「🗓️ 公式」「テーマ史」と出た。
- 原因は `app.js` ではなく `index.base.html` のほうだった。タブの**絵文字**と「テーマ史」という**ラベル**が固定文字列のまま残っていた。さらに前後ボタンの `title="前の時代"`、検索欄の `placeholder="用語・人物・できごとを検索"` も社会の語だった。
- 対処: `apps.json` に `listIcon` / `themeWord` / `kinds` を足し、生成時に置き換えるようにした。`app.js` 側も検索結果の種別ラベルを `APP.kinds` から読むようにした。
- **教訓**: 「分野ごとに変わる語を `APP` に出す」という方針は、`app.js` だけでなく**雛形HTMLにも同じだけ適用する**。生成後のページを目で見るまで、どこに直書きが残っているかは分からない。

### 7.2 絵文字の重複に気づきにくい
- 一覧タブに `📊` を割り当てたら、記録タブの `📊` と同じになった。タブが2つとも同じ絵文字で並んでいた。
- 生成後にタブのラベルを一度まとめて出力して、重複がないか確かめるとよい。

### 7.3 言語チェックの基準は教科で変える必要がある
- 社会では「2文字以上のラテン文字」を全部拾えばよかった（`village` `market` などの混入を検出できた）。
- 理科で同じ基準を使うと、`mg` `kx` `at` `ZnSO` `IBLsinθ` といった数式・化学式が大量に引っかかる。許可リストに足していく方法では追いつかない。
- 最終的に「**4文字以上で、かつ全部小文字か先頭だけ大文字の語**（＝ふつうの英単語の形）」だけを検出する規則に切り替えた。`ZnSO` のように途中に大文字が入るものは化学式として除外される。
- 社会と理科で基準を切り替えられるよう、検証スクリプトは教科をフォルダ名から判定している。

### 7.4 `ord`（配列問題）は同点を作らない
- 「大きい順に並べよ」の3つの値が2つ同じになると、正解が一意に決まらない。作問中に2問やってしまった。
- 作ったあとに値を並べて確認する。検証スクリプトでは検出できないので、作問時に気をつけるしかない。

### 7.5 `people` は分野によって意味を変えてよい
- 社会では「おもな人物」だったフィールドを、理科では「まちがえやすい区別」に流用した（「P波とS波」「同位体と同素体」など）。
- データ構造を増やさずに、見出しだけ `APP.wordsHeads` で切り替えている。**器は同じで中身の意味を変える**ほうが、新しいフィールドを足すより安全だった。

### 7.6 公開前は絶対パスの有無を必ず確かめる
- サブディレクトリ（`example.com/gakushu/`）で公開する可能性があるなら、`src` と `href` に `/` で始まるパスが1つもないことを確認する。
- ブラウザのコンソールで次を実行すれば一度に分かる。
  ```js
  [...document.querySelectorAll('[src],[href]')]
    .map(e => e.getAttribute('src') || e.getAttribute('href'))
    .filter(v => v && v.startsWith('/'))
  ```

## 8. 英語を足して分かったこと（2026-10-20 追記）

### 8.1 「英語の教材」でも、解説は日本語で書くほうが学習になる
- 設問文も選択肢も解説もすべて日本語にし、英語は**例として示すだけ**にした。英文には必ず訳と、どこを見れば判断できるかの考え方を添える。
- 英語で解説すると「英語が読めないと解説も読めない」という循環になる。共通テストの設問文自体が日本語なので、形式も合う。
- 結果として、他の17分野とまったく同じ `APP` 設定・同じ検証スクリプトで通せた。英語だけ特別扱いしなくてよくなった。

### 8.2 言語チェックは英語だけ基準を反転させる
- 7.3 で決めた「ふつうの英単語の形をした語を検出する」規則は、英語では**全部ひっかかる**。例文が英語だから当然。
- そこで英語の3分野だけ最小語長を事実上無効（`MIN=999`）にし、**キリル文字・ハングル・アラビア文字だけを検出する**ようにした。
- 混入の実害（長い日本語を書くと別言語の単語が混ざる、2.1）は英語でも起きるので、検出をゼロにはしない。ラテン文字の例外を認めるだけにとどめる。

### 8.3 シャッフルしない形式の偏りは、分野を足すたびに必ず再発する
- 2.8 で分かった `cmb` / `ord` の正解位置の偏りは、18分野すべてで起きた。18回とも検証スクリプトが見つけた。
- 作問のときは「正しい文を a に置く」「古い順に Ⅰ Ⅱ Ⅲ と書く」のが自然なので、**人が書くかぎり必ず偏る**。
- 直す作業も毎回同じなので、スクリプト化した。`cmb` は c と d の文を入れ替えて `a` を 0→1 / 2→3 にずらす、`ord` は Ⅰ Ⅱ Ⅲ の中身を入れ替えて別の正解番号にする。
- **`ord` の入れ替えで事故ったこと**: Ⅰ Ⅱ Ⅲ のラベル置換を問題ブロック全体にかけてしまい、設問文（「次のⅠ〜Ⅲを」）と `choices` 配列まで書き換わって正解が合わなくなった。置換は `exp:` 以降だけに限定する。

### 8.4 先に作った分野は、あとから直すまで偏ったままだった（2026-10-20 追記）
- 2.8 に気づいたのは数学を書いていたときで、それ以降の分野は作成時に直していたつもりだった。英語を仕上げたあとに全18分野を測り直したところ、**直っていたのは国語3分野と英語3分野だけ**だった。
- 実態はかなりひどく、社会4分野と理科4分野では **`cmb` の正解が全問①**（221問）。組合せ問題は常に①を選べば必ず当たる状態だった。`ord` も最大57%が1か所に寄っていた。
- 数学3分野も中途半端で、`cmb` は最大50%、数学Ⅱ・Bにいたっては②が0問・⑥（`ord`）も0問だった。**「直したつもり」がいちばん危ない。**
- 教訓は「気づいた改善は、気づいた時点で既存のぶんにも適用し、適用できたことを数字で確かめる」。新しく作るものだけ直すと、**直っている分野と直っていない分野が混在して、あとから見分けがつかなくなる**。測り直すまで誰も気づかない。
- 対策として、偏りを一覧する小さなスクリプト（全分野の `cmb` / `ord` の正解位置を並べて最大割合を出すだけ）を用意した。分野を足したら全分野を測る。1分野だけ測っても意味がない。
- 最終的に12分野（社会5・理科4・数学3）を直し、全18分野で `cmb` は最大27%、`ord` は最大25%に収まった。直した分野はすべてブラウザで全問に正解して満点になることを確かめている。

### 8.5 一括修正は、分野ごとの「書き方の揺れ」で止まる
- 9分野ぶんを一括で直そうとして、同じスクリプトが通らなかった。原因はデータの書き方が分野ごとに揺れていたこと。
- **組合せの選択肢が2通りあった。** 新しい分野は `['a・c','a・d','b・c','b・d']`（{a,b} から1つ・{c,d} から1つ）。古い社会4分野は `['a・b','a・d','b・c','c・d']`（正しい文が2つ・誤りが2つ）。前者にだけ 2.6 の構造規則が効くので、検証スクリプトの規則も選択肢の並びを見て切り替えるようにした。
- **記号のあとの区切りが半角スペースと全角スペースの両方あった。** スクリプトは区切りを決め打ちせず、`\na` の次の1文字を読んで判定する。
- **解説の書き方も違った。** 「正解は①a・c。」で始まる分野と、「a・bが正しい。」で始まる分野と、記号にまったく触れない分野（理科はほぼこれ）がある。記号に触れない分野がいちばん安全で、中身を入れ替えても解説を直す必要がない。
- 記号の置換は**単語の一部を巻き込む**。`independently` の `d`、`rad` の `d` のような例があるので、前後が英数字でないものだけを置換する。
- 直したあとは、解説が「正しい」と言う記号と `a` が指す選択肢、「誤り」と言う記号と誤答の組を**機械的に突き合わせる**。ブラウザの全問採点は `a` と選択肢の対応しか見ないので、解説の矛盾はここでしか見つからない。
- この突き合わせを全18分野（組合せ541問・配列501問）にかけたところ、**今回いじっていない分野から6件の矛盾が出た**。
  英文読解で4件（最後の一文が正解の d を「誤り」と呼んでいた。以前の一括置換が「dも誤り」しか拾えず、「dも位置で決めつけており誤り」を取りこぼしていた）、数学Ⅰ・Aで1件（期待値の大小が解説の中で食い違い、`a` 自体が誤っていた）、漢文で1件（`a` と解説の丸数字がずれていた）。
- つまり**一括置換は「取りこぼし」で壊れる**。置換パターンを足していくより、置換後に突き合わせる仕組みを持つほうが確実だった。
- 言い回しの除外も要る。「cのとおり言いすぎの選択肢は誤りの定番である」は記号 c を誤りと呼んでいるのではないので、`Xのとおり` は対象から外す。

### 8.6 `sel` / `src` も、設定でシャッフルを切るとそのまま偏りが出る（2026-10-20 追記）

- 8.4 で直したのは `cmb` と `ord` だけだった。`sel`（正誤判定）と `src`（短文・資料）は出題時にシャッフルされるので、既定の設定では偏りが見えない。**それで後回しにしていた。**
- しかし設定の「選択肢の順番をシャッフルする」を切ると、データの並びがそのまま画面に出る。そして実際の偏りは `cmb` 以上にひどかった。理科/化学は `sel` 90問のうち66問が①・②が1問・③が0問、理科/地学は `sel` 90問のうち86問が①、社会/政治・経済は `src` 12問すべてが①。**シャッフルを切った人には「迷ったら①」で6〜9割当たってしまう。**
- 全19分野で測り直し、`sel`・`src` とも最大26〜31%（しきい値35%）に収めた。962問の正解位置を動かした。
- **直し方が `cmb` / `ord` とは違う。** `cmb` は選択肢の記号の中身（a〜d の文）を入れ替えればよかったが、`sel` / `src` は `choices` 配列そのものを並べ替えて `a` を対応させることになる。そのうえで**解説の中の丸数字をすべて付け替える**。
- 並べ替えは「正解の文を配列から抜いて、目標の位置に差し込む」方式にした。残り3つの相対順序が変わらないので、解説が誤答に触れる順序（①→②→④…）が崩れない。入れ替え（2点交換）やローテーションにすると、解説の中の番号が「④→①→②」のように前後して読みにくくなる。
- **丸数字の置換は二段階で行う（旧番号 → 仮の記号 → 新番号）。** 一段階でやると、先に置き換えた番号をもう一度置き換えてしまう。たとえば ①→② と ②→③ を順に当てると、もとの ① が ③ になる。
- **置換は `exp` に限定する。** 設問文の「次の①〜④のうちから一つ選べ」は全2353問にあり、ここを書き換えると問題が壊れる。8.3 の `ord` の事故とまったく同じ構図なので、同じ対策（置換範囲をフィールド単位で切る）を取った。

### 8.7 丸数字が選択肢を指していない問題がある

- 全分野を機械的に置換する前に、`src` と `choices` の中の丸数字を調べた。4問だけ、丸数字が選択肢ではないものを指していた。
  - 理科/化学の2問（`q-kg-141` `q-kg-160`）… `src` の「① 希塩酸を加えて…」が**操作の番号**で、解説の「①で銀イオンが…」はそれを指している。
  - 国語/現代文の1問（`q-danraku-11`）… `choices` が `['①の文','②の文','③の文','④の文']` で、`src` の各文を指している。並べ替えると ① の位置に「②の文」が出て意味をなさない。
- これらは並べ替えの対象から外した（スクリプト側で「`src` か `choices` に丸数字があれば動かさない」と判定する）。
- 同じ理由で、**選択肢が数値の昇順・降順に並んでいる計算問題**（理科4分野の34問）も外した。`['10 N','20 N','30 N','40 N']` を並べ替えると不自然に見える。
- 偏りは「動かせる問題」だけで十分に均せたので、無理に全問を動かす必要はなかった。**均すのは分野ごとの分布であって、1問ずつではない。**

### 8.8 解説の「途中に出てくる」丸数字を照合する仕組みがなかった

- 既存の検証は `正解は③` と `^③が正しい` だけを見ていた。しかし解説はほぼ全問で複数の丸数字に触れる（「③が正しい。…①は誤りで…②も誤りで…④も誤りで…」）。**途中の番号がずれても誰も気づけない状態だった。**
- そこで `tools/check/xsel.js` を足した。解説の中の「丸数字＋助詞＋評価（正しい／誤り）」を全部拾い、`a` が逆向きに断定されていないかを見る。`lib.js` の `expRefErrors()` に本体を置いて `chk.js` からも呼ぶ。全19分野の1360問（解説に丸数字がある `sel`・`src`）にかけて矛盾0。
- **「①が正しい」側は判定に使えない。** 「最も適当なものを選べ」の問題では、正解でない選択肢も「正しい用法である」「適切な手順である」と書かれることがある（9問あった）。`a` が逆向きに断定されていないかだけを見るのが安全だった。
- 解説の冒頭が**誤答の説明から始まる**問題もある（「②は同化主義。」で始まり、正解は①）。冒頭の丸数字を機械的に正解と見なすと誤検出する。評価の語（正しい／誤り）が直後に続くときだけ正解の断定と見なす。
- 移行そのものの検証は別に作った。作業前のバックアップと突き合わせ、①選択肢の集合が変わっていない ②`choices[a]` の文が変わっていない ③並べ替えから導いた対応表で旧解説を付け替えると新解説に一致する、の3点を2353問すべてで確かめた。**「結果が正しいか」だけでなく「変換が可逆か」を見ると、スクリプトのバグがそのまま出る。**
- 最後にブラウザで全19分野を全問採点した。**シャッフル入りとシャッフル切りの両方**で満点（計6910問）。シャッフル切りでは「画面の並びがデータの並びと一致しているか」「表示される正解番号が解説の断定と一致しているか」も同時に見た。今回の修正はまさにこの状態のためのものなので、ここを確かめないと意味がない。

### 8.9 書き下ろしの例文は、分野をまたいで方針をそろえる
- 現代文で決めた「本文資料はすべて書き下ろし、実在の作品は引用しない」を、英語の英文資料にもそのまま適用した。
- 古文・漢文だけは例外で、著作権の保護期間を過ぎた古典を引いている。
- 方針を分野ごとに考えると後から判断がぶれるので、**教科を足す最初の時点で決めて README に書いておく**。

## 9. ポータル横断の検索を足して分かったこと

### 9.1 索引に説明文まで入れると、容量が跳ね上がる
- ポータルから270単元を横断検索したいので、全分野の `data-units.js` から索引を生成した（`tools/tpl/mkindex.js`）。
- 最初は用語の説明文（`d`）も入れようとしたが、18分野ぶんでは数MBになる。ポータルを開くたびに読むファイルなので、オフラインでも初回表示が重くなる。
- **索引には単元の見出し（名前・よみ・サブタイトル・キャッチ・絵文字）と、用語・人物の「名前だけ」**を入れた。270単元・用語3758件で約150KB に収まった。
- 説明文の検索は各アプリの🔍に任せる。**「どこで何を検索するか」を階層で分ける**と、容量と機能の両方が成立する。

### 9.2 1つの `search.js` をポータルと教科ページで共有する
- ポータル（全教科）と教科ページ（その教科だけ）で、検索の見た目と動きは同じ。スクリプトを2本に分けると同じ修正を2回することになる。
- `document.body.dataset.subject`（教科ページでは `"社会"`、ポータルでは空）で対象を絞り、`document.body.dataset.base`（教科ページでは `"../"`）でリンクの相対パスを切り替えた。HTML 側の属性だけで両方に対応できる。
- 1.1 と同じ考え方。**差は属性やデータに置き、コードは1本にする。**

### 9.3 検索結果から単元を直接開く導線が要る
- 検索で単元が見つかっても、アプリのトップに飛ぶだけでは探し直しになる。
- 各アプリの `app.js` に `#u=<単元ID>`（任意で `&s=<サブタブ>`）を読むハンドラを置き、**初回読み込みと `hashchange` の両方**で動かした。片方だけだと、同じアプリ内で別の単元を開くときに反応しない。
- URL に単元 ID が入るので、特定の単元をブックマークしたり共有したりもできるようになった。

### 9.4 索引の `?v=` は6枚そろえる
- 索引を作り直したら、ポータルと教科ページ5枚の `?v=` を**同じ番号に揃える**。
- 1枚だけ上げ忘れると、そのページだけ古い索引を読み続ける。新しく足した分野が「ポータルからは出るのに教科ページからは出ない」という形で現れる。
- 分野を足す手順は「データを書く → 検証 → `mkindex.js` → `?v=` を6枚＋`sw.js` の `CACHE`」で固定した。

## 12. 青空文庫から読み物を作って分かったこと（2026-10-20 追記）

### 12.1 収録の可否は、目録の著作権フラグで機械的に決められる
- 青空文庫は全作品の目録（`list_person_all_extended_utf8.csv`、約19,500件）を配っており、**作品著作権フラグ**・底本・入力者・テキストURLがすべて入っている。
- 候補を挙げてからこの目録に当てれば、入れてよいかどうかを人手の判断なしに確かめられる。今回は30件中29件が「なし（＝保護期間満了）」で、志賀直哉『城の崎にて』だけが収録なしだった。1971年没なので、2018年の保護期間延長（50年→70年）に掛かってまだ満了していない。
- **「有名だから公開されているはず」は通らない。** 没年と延長の経過措置まで見ないと判断できないので、目録に当てるのが唯一の確実な手順になる。

### 12.2 注記は入れ子になることがある
- `［＃[^］]*］` で注記を消すと、`［＃「はつきり［＃「はつきり」に傍点］と」は底本では…］` のような入れ子で**外側の尻尾が本文に残る**。全30作品で1か所だけ起きた。
- 正しくは、中に `［＃` を含まないもの（＝いちばん内側）から順に消す：`［＃(?:(?!［＃)[^］])*］` を、無くなるまで繰り返す。
- 1,596,386字のうちのたった1か所だが、**検証スクリプトを書いていなければ絶対に見つからなかった**。

### 12.3 外字注記は面区点番号から実際の文字に戻せる
- `※［＃「赤＋報のつくり」、第3水準1-15-5］` のような外字注記は、面区点を `euc_jis_2004` のバイト列に組み立てて decode すれば実際の文字になる。317件中270件がこれで解決した。
- 残り47件は末尾が「底本のページと行」で面区点ではないもの。`U+` の併記があればそれを使い、無ければ手当て表で埋める（白ゴマ点→﹆、「赤＋報のつくり」→赧 など）。
- **`〓` を1字でも残さないことを検証条件にしておく**と、埋め忘れがそのまま検出される。

### 12.4 字数の数え方を2つのアプリでそろえていなかった
- 読み物の段落は先頭1字が種類（`p`／`w` など）。古典文学は `chars[1]` を**この1字まで含めて**数えており、近現代文学は含めずに数えていた。古典文学の原文が段落数ぶん（3,328字）多く出ていた。
- JavaScript の `String.length` は UTF-16 の数なので、**BMP 外の漢字（𢪸・𨋳・𤄃 など）が2字と数えられる**。Python の `len()` とずれる。検証側は `[...s].length` で文字数を数える。
- どちらも「表示が少しずれる」だけの小さな違いだが、**2つの実装で同じ値を出す検証を書いた瞬間に露見した**。器を共有するなら、数え方も1か所に決める。

### 12.5 版を上げるたびに、保存した本文が消えていた
- Service Worker の `activate` で「`CACHE` 以外のキャッシュを全部消す」書き方をしていたため、`?v=` を上げるたびに**オフライン用に保存した本文（古典文学2.6MB＋近現代文学1.6MB）が丸ごと消えて取り直し**になっていた。
- 骨組み用（版つき）と本文用（版なし）で**キャッシュを2つに分ける**のが正しい。`activate` はその2つを残し、`fetch` は URL に `/text/` を含むかどうかで入れ先を変える。
- 本文そのものを直したときは、`APP.textVer` を上げて本文のURLを変える。骨組みの版とは独立に動かせる。

### 12.6 読み物にも、クイズの `chk.js` にあたる検証が要る
- クイズ19分野には `chk.js` 以下の検証があったが、読み物には何も無かった。今回 `tools/check/reader.js` を足し、`all.js` から呼ぶようにした。
- 見るのは、キャッシュ名と `?v=` の整合・章番号の連番・要約の有無・本文ファイルの存在と `TEXT()` の番号・字数の一致・注記の消し残し・外字の残り・段落の種類・ルビ記法の対応・日本語以外の文字。
- **足した初回に、以前の取りこみで消し残していた底本注記が古典文学に5か所見つかった。** 検証は足した時点から過去にも効く。

## 13. 文豪紹介を足して分かったこと（2026-10-20 追記）

### 13.1 肖像写真は、ライセンスを機械で確かめてから使う
- ウィキメディア・コモンズは API で `extmetadata.LicenseShortName` を返すので、**「Public domain で始まるものだけ採る」という判定をスクリプトに書ける**。26人中、日本語版ウィキペディアの代表画像をそのまま使えたのは25人で、芥川龍之介だけが CC BY-SA だった。
- 有名な人物ほど、代表画像が最近の加工版（着色・トリミング）に差し替わっていることがある。**「有名な写真だから古い＝保護期間満了」とは限らない。**
- ライセンスが通っても、**画像として使えるかは別問題**。120×179 と小さすぎるもの、部屋の引き写真で顔が豆粒のもの、額縁とキャプションごと複写したものがあった。並べた一覧を1枚の画像にして目で見るのがいちばん早い。

### 13.2 `loading="lazy"` は、画面に出ない状況では永遠に読み込まれない
- 肖像をすべて `loading="lazy"` にしたところ、ブラウザのペインを隠した状態での自動検証で「画像が読めない」が多発した。隠れたページでは要素が可視領域に入らないので、遅延読み込みが始まらない。
- **一覧の小さな写真は lazy、詳細ページの大きな1枚は eager** と使い分けるのが正しい。詳細ページは必ず見られる1枚なので、遅延させる意味がそもそもない。
- 検証の側も、`naturalWidth > 0` だけでは「まだ読み込んでいない」と「読み込みに失敗した」を区別できない。`fetch` で HTTP ステータスを直接見ると切り分けられる。

### 13.3 共用の app.js に機能を足すときは、データの有無で分岐させる
- 文豪紹介は近現代文学にしか無いが、app.js は古典文学と同一ファイルのまま保った。`AUTHORS` が定義されていなければ画面もタブも作らない、という一行の分岐で済む。
- `show()` のように画面名を並べる関数は、**要素が無い場合に落ちないようにしておく**（`if (e)` を入れる）。ここを忘れると、片方の分野だけが真っ白になる。

### 13.4 ヒアドキュメント経由の Python は、逆スラッシュが落ちることがある
- `cat > x.py <<'PY' … PY` で書いたスクリプトの中の `"\\n"` や `"\\'"` が、1つの逆スラッシュに潰れていた。そのため `'` のエスケープが効かず、生成した JavaScript が `Unexpected identifier` で落ちた（谷崎潤一郎の写真ファイル名に `'` が入っていた）。
- 同じ理由で `console.log('\n…')` が実際の改行になり、文字列が閉じないという壊れ方もした。
- **エスケープを含むコードは、ヒアドキュメントではなくファイル書き込みツールで置く**か、`chr(92)` / `chr(39)` のように数値で書く。生成したファイルは必ず `node --check` に通す。

## 14. 説明に図・表・地図・写真を足して分かったこと（2026-10-21 追記）

### 14.1 既存のデータに手を入れずに足す

`UNITS` はどの分野も数千行ある。ここに図版を書き足すと、差分が読めなくなり、既存データを壊す危険も上がる。
別ファイル `data-figs.js` に `FIGS = { 単元id: [図版, …] }` として外付けし、アプリ側は

```js
function figsOf(e) {
  if (typeof FIGS !== 'undefined' && FIGS[e.id]) return FIGS[e.id];
  return e.figs || [];
}
```

で拾う形にした。`data-figs.js` が無い分野でも動く。19分野ぶんを並行して書けたのは、この切り離しのおかげ。

### 14.2 SVG に色を直書きしない

図を描くとき `fill="#1a73e8"` と書いてしまうと、暗い画面やセピアで読めなくなる。
配色はすべて `var(--primary)` `var(--text)` `var(--muted)` `var(--surface)` `var(--surface2)` `var(--border)` に寄せ、検証スクリプトで `#rrggbb` が入っていたら落とすようにした。
`viewBox` を付けて幅は CSS に任せると、横380pxの画面でも崩れない。

### 14.3 写真は権利の確認を自動にする

ウィキメディア・コモンズの画像は、ライセンスがまちまち。目で見て選ぶと必ず取り違える。
API の `extmetadata.LicenseShortName` を読み、`public domain` `cc0` `no restrictions` のどれかでなければ落とす、という門を通してから落とす形にした。
落としたあとも `tools/check/figs.js` が `credit` の表記を見て、同じ条件を満たさなければ失敗する。二重に見ている。

写真は 720×620・画質72 に縮めて130KB以下にそろえた。94点で5.2MBに収まり、まとめて保存しても現実的な大きさになる。

### 14.4 自分の書いた文に外国語がまぎれる

図版を大量に書いていると、日本語の文のなかに英単語やロシア語がまぎれることが何度もあった
（`законではなく`、`내용を置き換える`、`village ごとの石高`、`例・данные・理由で支える` など）。
2.1 と同じ失敗だが、量が増えるほど確実に起きる。
`tools/check/figs.js` で見出し・説明・表のセルを調べるようにし、**図の中の文字もタグを外して調べる**ように直した。
最初は表だけを見ていて、SVG のなかのロシア語を取りこぼした。チェックは、人が書ける場所すべてに掛けないと意味がない。

### 14.5 図版を入れる単元を選ばない

19分野285単元すべてに1点以上入れた。「効きそうな単元だけ」にすると、入っている単元と入っていない単元の見た目が不ぞろいになり、かえって読みにくい。
表が向く単元（活用表・句法・年表）、図が向く単元（手順・対比・時間の流れ）、写真が向く単元（遺跡・生物・地形）、地図が向く単元（歴史・地理）と、題材で種類を選び分けた結果が、表295点・図212点・地図23点・写真94点。

### 14.6 版を上げる順序

`index.html` の `?v=N` と `sw.js` の `CACHE = '<slug>-vN'` は必ずそろえる。
今回は先に全19分野へ空の `data-figs.js` と読み込み・版上げを入れてしまい、中身は後から埋めた。
こうすると、中身を書くときに版のことを考えなくてよい（まだ公開していないので、利用者が空の版を受け取ることはない）。

## 15. ドキュメントが現物に追いつかなくなる（2026-10-21 追記）

### 15.1 数字は「そのとき直す」以外に方法がない

分野を18から19に増やしたとき、ドキュメントの「18分野」を直さなかった。
あとで数えたら、README・設計書・知見の3ファイルに**20か所**散らばっていた。
さらに厄介なのは、その20か所が2種類まざっていたこと。

- **現状を述べている記述**（設計書の見出し「18分野共通」、「1つのエンジンを18分野で共有するしくみ」）→ 直すべき
- **当時の経緯を述べている記述**（知見の「18分野まで広げて分かったこと」という追記章）→ 残すべき

一括置換では直せない。1か所ずつ前後を読んで仕分けるしかなく、結局それだけで1セッションかかった。
**分野や機能を足した回に、そのつど直す。** まとめて直そうとすると、必ずこの仕分けが発生する。

### 15.2 追記章は日付をつけて積む、本文は上書きする

知見は「○○を足して分かったこと（日付）」という章を積み上げる形にしている。これは**そのときの判断の記録**なので、あとから数字を書き換えない。
いっぽう README と設計書は**今どうなっているか**を書く場所なので、古い記述は上書きする。
この2つを混ぜると、15.1 の仕分けができなくなる。章の性格を先に決めておく。

### 15.3 ドキュメントにも検証がいる

データには `tools/check/` があるのに、ドキュメントには何もなかった。結果、
README の収録量の表には漢検2級の行が無く、設計書の索引の件数は実測とずれ、再現プロンプトの読み物の欄は源氏物語1作品のままだった。
いずれも「足したときに書き足さなかった」もの。
せめて、分野数・単元数・問題数・図版数のような**数えられる数字**は、実データから出して突き合わせられるようにしておくとよかった。

### 15.4 再現プロンプトは「作り直せるか」で点検する

再現プロンプトは、読み返すだけでは抜けに気づけない。
**「これだけを渡されて同じものが作れるか」**を基準に読むと抜けが見える。今回それで見つかったのは次の3つ。

- 図・表・地図・写真のしくみ（`data-figs.js`）がまるごと無かった
- 読み物2分野の作り方（本文の分割読み・段落の種類・ふりがな・キャッシュの分離）が1行も無かった
- ポートの一覧が3つぶん足りなかった

どれも「あとで書こう」と思ったまま残ったもの。**機能を足した回に書く**のが、ここでも結論になる。

## 16. 検証スクリプト自身が壊れていた（2026-10-21 追記）

### 16.1 一時ファイル名をパスの末尾から作ると、分野をまたいで衝突する

- **症状**: `node tools/check/all.js` が「読み物NG」と出る。近現代文学で「本文ファイルがない」が143件。
  ところが挙がっているのは `genji/1` … `genji/54`、つまり**古典文学の作品ID**だった。
  キャッシュ名の照合も `APP.cache=kotenbungaku-v8 / sw.js=kingendai-v2` という、ありえない組み合わせになっていた。
- **原因**: `reader.js` の `load()` が、データを一時ファイルに書き出して `require()` する方式だった。

  `国語/古典文学/data-works.js` と `国語/近現代文学/data-works.js` が**同じ名前になった**（どちらも「文学/data-works.js」で終わる）。
  さらに `os.tmpdir()` は `/var/folders/…` を返すが `require.cache` のキーは実体の `/private/var/…` なので、
  `delete require.cache[p]` も効かない。結果、2つ目を読んだつもりで1つ目のモジュールが返っていた。
- **対処**: 一時ファイルをやめ、`lib.js` と同じ `new Function` 方式にした（偽の `module` を渡して `module.exports` を取り出す）。

- **本当の問題は、検証が通っていなかったことではない。** エラーが出ていたから気づけた。
  怖いのは逆のほうで、**近現代文学は足してから一度も実際に検証されていなかった**。
  12.6 で「読み物にも検証が要る」と書いて `reader.js` を足したのに、2分野目を足した時点で中身は古典文学の二重チェックになっていた。
- **教訓**: 検証スクリプトは、**同じものを2つ通したときに違う結果が出ることを確かめる。**

### 16.4 「最終更新」の日付は、コミット前にしか気づけない（2026-10-21 追記）

- 日付の照合も `docs.js` に入れた。現状を述べる6本に `最終更新: YYYY-MM-DD` の行があるかを見て、

  そのままスクリプトの対象の線引きになった。**章の性格を先に決めておくと、機械にかける範囲も決まる。**

### 16.5 `ls` に見えないファイルが検証を落とす

- **症状**: `node tools/check/all.js` が「読み物NG」。英米文学で「使われていない肖像: ._alcott.jpg」が10件。

- **原因**: macOS で作った `._名前.jpg`（リソースフォークの入れ物。中身は画像ではない）が、
  Windows へ移したときに実体のファイルとして残っていた。`ls` はドットで始まる名前を隠すが、
  **`fs.readdirSync` は返す**。`.endsWith('.jpg')` を通ってしまうので、使われていない写真として挙がる。
  リポジトリ全体で323件あり、`.git/objects/pack/` にも1件あって、git のコマンドが毎回
  `error: non-monotonic index` を出していた。
- **`.gitignore` には最初から `._*` が入っていた。** つまり「無視する」という判断はできていて、
  git だけがそれを知っていた。**同じ判断を、ファイルを数える側は持っていなかった。**
- **対処**: `lib.js` に `jpgsIn()` を置き、`reader.js` と `figs.js` の両方から呼ぶようにした。
  18.4（同じ判断基準が2か所にあると片方だけ古くなる）と同じ形なので、最初から1か所にした。
  ローカルの323件は消した（git の追跡外なので、消しても差分は出ない）。
- **直ったのが検査のほうだと確かめる手順**: ファイルを消す前に検査を走らせ、通ることを見た。
  先に消すと、検査を直したからなのかファイルが無くなったからなのか区別がつかない。
  16.2 で「検証を足すときは落ちることを先に確かめる」と書いたが、**直すときは逆に、
  原因を残したまま通ることを確かめる。**
- 11章（Mac → Windows）の続きでもある。環境を移して壊れるのはパスだけではなく、
  **片方の OS にしか意味のないファイルが、もう片方では普通のファイルとして見える**ことでも起きる。

## 17. 英米文学（英語の読み物）を足して分かったこと（2026-10-21 追記）

### 17.1 日本語訳は「あるか」ではなく「読めるか」で選ぶ

- 英語の原文に日本語訳を添えるつもりで、青空文庫の目録から保護期間の満了した訳を探した。
  10冊の候補のうち6冊に訳があり、権利の上では全部使える。
- ところが目録の**文字遣い種別**を見ると、アリスの訳（丸山英観『愛ちやんの夢物語』1910年）は**旧字旧仮名**だった。
  「愛ちやん」「姊《ねえ》さん」の調子で、いまの高校生には英語の原文より読みにくい。学習の助けにはならない。
- 権利（著作権フラグ）と可読性（文字遣い種別）は**別の軸**で、目録はどちらも持っている。
  判定はどちらも機械でできるのに、最初は権利しか見ていなかった。
- 結論として、新字新仮名の訳（ホームズ8編・若草物語・クリスマス・カロル・荒野の呼び声）は学習用の訳として併載し、
  旧字旧仮名のものは「明治の訳」と名前を変えて、何であるかを明示したうえで読み物として載せることにした。
  **隠すのでも、黙って学習用として出すのでもなく、ラベルを変える。**

### 17.2 語注は、原文と突き合わせないと必ずずれる

- 章ごとに「英検2級の語彙をこえる語」を10〜12語そえた。アリス12章で122件。
- 書いたあとに原文と突き合わせたら、**18件がその章に出てこなかった**。記憶で「アリスならこの語が出るはず」と書いたものである。
  `sobbing` `spectacles` `indignantly` のように、いかにもありそうで、実際には別の章にしかない語が混ざる。
- `tools/check/reader.js` に突き合わせを入れた。語注の見出しがその章の原文に（大文字小文字を問わず）出てくるかを見るだけだが、
  これで18件すべてが落ちた。差し替えの候補も、原文から実在する語を拾って選んだ。
- 2.1（長い日本語を書くと別言語がまぎれる）と同じ構図で、**書いたものと素材を突き合わせる検査**が要る。
  内容の良し悪しではなく、実在するかどうかなら機械で見られる。

### 17.3 外字は、注記を消す前に直す

- 青空文庫の取りこみで `姊《ねえ》さん` が `※《ねえ》さん` になった。
- 原因は順番で、`［＃…］` の注記を先に消してから外字 `※［＃…］` を直そうとしていた。
  注記を消した時点で外字の説明がなくなり、記号の `※` だけが残る。**外字を先に直してから注記を消す。**
- 317件のうち316件は面区点から戻せた。残り1件は `※［＃「※」は底本では「』」の転倒］` で、
  これは外字ではなく「底本の組み方」の注記だった。手当て表で `『` に替えた（12.3 と同じ扱い）。

### 17.4 既存のデータと同じ書き方にそろえる

- 二倍の踊り字 `／＼` を元の文字列に戻そうとしたが、ルビをまたぐ場合（`恐《おそ》る／＼`）に
  直前の2文字が `》る` になってしまい、壊れた。
- 近現代文学の本文を見たら、**32ファイルに `／＼` がそのまま残っていた**。ルビ記法と同じく、青空文庫の書き方を残す方針だった。
- どこまでを繰り返すのかが一意に決まらない以上、展開しないのが正しい。**既存のデータを見てから直し方を決める。**
  自分で「正しい形」を決める前に、同じものを先に扱った場所を見る。

### 17.5 16.1 の取り違えは、別のスクリプトにも同じ形で埋まっていた

- 3つ目の読み物を足して索引を作り直したら、単元が610件から566件に**減った**。
- `tools/tpl/mkindex.js` の `load()` が、`reader.js` とまったく同じ方式（一時ファイル名をパスの末尾20バイトから作る）だった。
  古典文学・近現代文学・英米文学はどれも「…文学/data-works.js」で終わるので、3つが同じ名前に衝突していた。
- **なぜ今まで出なかったのか。** `os.tmpdir()` がシンボリックリンクでない環境（Windows など）では `require.cache` の削除が効き、
  衝突しても正しく読める。この索引は Windows で作られていた（11章）。Mac で作り直した瞬間に出た。
- 16.1 で「検証する側も検証がいる」と書いたが、足りなかった。**同じ書き方をした場所が他にないかを探すところまでが対処である。**
  1か所直して終わりにすると、残りは環境が変わった日に出る。

### 17.6 「最初に見せる本文」は分野で違う

- 読み物の章を開くと、まず訳が出る作りだった。古典文学も近現代文学も日本語の本で、それが正しい。
- 英米文学では逆で、**まず英語の原文を見せたい**。訳は確かめるために開くものである。
- `app.js` に書いてあった「訳を先に出す」を `APP.firstType` に出した。1.2（画面に出る語を APP に出す）と同じことが、
  語ではなく**既定の動作**で起きた。横展開で疑うべきなのは文字列だけではない。

### 17.7 語注は「辞書を作って割り当てる」ほうが、章ごとに書くより正確だった

- 10作品170章に語注を付けることになり、章ごとに10語ずつ書くと1700件になる。最初の4冊は手で書いたが、
  残り5冊（133章）でやり方を変えた。
- **章ごとに書くのではなく、語の辞書をひとつ作り、各章に実在する語を機械で割り当てる。**
  手順は、①各章から「珍しくて長い語」を抜き出して候補の山をつくる ②よく出る語から順に日本語をつける
  （最終的に381語） ③各章について、辞書にあって本文に実在する語を最大8語、全体で出番の少ない語を優先して採る。
- 利点は2つ。**同じ語を何度も訳し直さずに済む**ことと、**実在しない語が原理的に入らない**こと。
  17.2 の失敗（122件中18件が実在しなかった）は、記憶から書いたために起きた。素材から選べば起きない。
- 欠点は、文脈に寄り添った説明にならないこと。言葉遊びや取りちがえのように、その章でしか意味を持たない語は
  この方法では拾えない。だから**アリスのように仕掛けが言葉そのものにある作品は手で書き**、
  筋を追う長編は辞書から割り当てる、と分けた。
- 割り当てたあと、5語に満たない章を洗い出して辞書を足す、を2回くりかえした。
  最後に残ったのはオズの最終章だけで、これは本文が375字しかない章だった。**薄いところを数える仕組みがあると、
  どこまで埋めるかの判断が早い。**

### 17.8 「文豪」という語が、索引生成にも埋まっていた

- 作家紹介を足したら、ポータルの検索結果に「ルイス・キャロル（文豪）」と出た。
- `app.js` の画面見出しと、`tools/tpl/mkindex.js` の索引ラベルの2か所に、`'文豪'` が直書きされていた。
  `APP.authorWord` に出し、近現代文学は「文豪」、英米文学は「作家」にした。
- 1.2（画面に出る語を APP に出す）と 7.1（雛形HTMLにも直書きが残る）の、**3か所目**である。
  生成スクリプトにも同じ目で当たらないといけない。画面に出る語は `app.js` と HTML だけにあるとは限らない。
- 見つかったのは、検索結果を目で見たからだった。**足した機能は、入口（アプリ）だけでなく、
  そこから出ていく先（索引・検索結果）も見る。**

### 17.9 肖像は、権利を確かめたあとに「使えるか」をもう一度見る

- 13.1 と同じ手順（ja.wikipedia の代表画像 → コモンズの API で `LicenseShortName` を確認）で10人ぶんを集めた。
  権利はこれで機械的に決まる。10人中9人は代表画像がそのまま使え、バリーだけは代表画像が無かった。
- ところが並べて見ると、**バリーは額縁ごと複写したもの、ボームは全身像で顔が小さく手書き文字入り**だった。
  どちらも権利は Public domain で、検査はすべて通る。13.1 でまったく同じことを書いていたのに、また起きた。
- ジャック・ロンドンも、代表画像は191×320で小さすぎた。**大きさは機械で弾けるが、構図は弾けない。**
  並べた一覧を1枚にして目で見る工程は、権利の確認とは別に必要である。
- 差し替えは、コモンズの検索を「Public domain・縦長・240×320以上」で絞ってから候補を数点落とし、
  また並べて選んだ。この二段構え（機械で絞る → 目で選ぶ）が、いまのところいちばん速い。

## 18. 人物だけの分野を足して分かったこと（2026-10-21 追記）

### 18.1 権利が通らないなら、載せないという選択をする

- 理科に「日本人のノーベル賞」を足すとき、作家紹介と同じく顔写真を置くつもりだった。
  28人ぶんを調べたところ、**Public domain の肖像があるのは3人だけ**（湯川秀樹・朝永振一郎・福井謙一）で、
  残りは CC BY が18人、CC BY-SA が5人、GFDL が1人、代表画像なしが1人だった。現代の人物なので当然である。
- 選べたのは3つ。方針どおり写真なしで作る／CC BY まで許す／CC BY-SA まで許す。
  **写真なしを選んだ。** 3人だけ写真があると見た目が不ぞろいになり（14.5 と同じ問題）、
  CC BY を許すと README・設計書・検証スクリプトの前提をすべて書き換えることになる。
- 大事なのは、**調べる前に決めないこと**だった。「作家紹介と同様に」という依頼を字義どおり受けて
  先に写真を集めはじめていたら、24人ぶんの無駄になっていた。権利の調査は、作りはじめる前に終わらせる。

### 18.2 事実の一覧は、自分の記憶ではなく出どころから取る

- 受賞者の一覧を自分で書き出すことはしなかった。日本語版ウィキペディアの記事と Wikidata から取り、
  両方の数を突き合わせている（物理12・化学12・医学6＝30のうち、日本出身でない2人を除いて28人）。
- 2026年の化学賞のように**学習データより新しい事実**が混じる。硤合憲三の受賞と、利根川進・白川英樹が
  2026年に亡くなったことは、記事の本文を取って確かめた。**知らないことを知らないまま書かない。**
- 一人ずつの略歴も、記事の冒頭（extract）を取ってから書いた。出身地・学位・所属のような細かい事実は、
  うろ覚えでいちばん間違える。

### 18.3 作品のない分野も、同じエンジンに乗せられた

- 読み物の `app.js` は「作品 → 巻 → 本文」を前提にしている。人物だけの分野はその前提から外れる。
- 分けずに済ませたのは、**WORKS が空かどうかで入口を変える**という一行の分岐を足しただけだったから。
  13.3（データの有無で分岐させる）と同じ考え方で、4分野目も `app.js` を同一のまま保てた。
- ついでに、人物ページの見出し（「略歴」「どんな作品を書いたか」）が直書きだったことが分かり、
  `APP.authorSections` に出した。17.8 と合わせて、**人物まわりの語は4か所に埋まっていた**ことになる。
  横展開のたびに同じ形で見つかるので、新しい分野を作るときは画面を一度すべて目で読むのが早い。

### 18.4 検証の基準は、分野を足すたびに教科に合わせ直す

- `reader.js` のラテン文字チェックは3文字以上で固定だった。理科に置いた分野では `iPS細胞` `GFP` のような
  略語が本文に出るので、全部ひっかかる。
- クイズ側は教科ごとに最小語長を変えている（7.3 / 11.2）。同じ `lib.js` の `minlenFor()` を読み物側でも使うようにした。
  **同じ判断基準が2か所にあると、片方だけ古くなる。** 最初から共有しておけばよかった。
- なお今回も、自分で書いた日本語のなかにロシア語が1語まぎれていた（「внутри に規則正しいすきま」）。
  2.1 から数えて何度目かも分からないが、検査があるかぎり必ず止まる。

## 19. 権利が通った写真が、被写体を外していた（2026-10-21 追記）

### 19.1 検査が見ているのは権利だけで、何が写っているかではない

建物の写真を見直したら、権利はすべて通っているのに**被写体そのものが違う**ものが並んでいた。

| 見出し | 実際に写っていたもの |
|---|---|
| 法隆寺 | 玉虫厨子（寺が所蔵する小さな厨子） |
| 国会議事堂 | 夜景の都心。議事堂は遠くの小さな点 |
| 日本銀行本店 | 北門の銘板（「日本銀行 北門」の文字だけ） |
| 平等院鳳凰堂 | 屋根の上の鳳凰のクローズアップ |
| 最高裁判所 | 擁壁と植えこみ。建物は上端が少し見えるだけ |
| 岩のドーム | ヘブライ語の説明が刷りこまれた古い銅版画 |

`tools/check/figs.js` は全部通していた。**当然で、見ているのは権利・大きさ・ファイルの有無だけである。**
14.3 で「権利は機械で決まる」と書き、17.9 で「構図は弾けない」と書いた。その次に出たのが、
構図ですらなく**題材そのものの取りちがえ**だった。弾ける範囲の外側は、毎回ひとつ外へ広がる。

### 19.2 検索語が合っていると、結果が合っている気になる

なぜ起きたか。`法隆寺` で検索して権利の通る最初の1件を採る、という作り（`img_get.py`）にしていた。
コモンズでは「法隆寺が所蔵する品」も「法隆寺」で当たる。**検索語は合っているのに、採れたものが別物になる。**
権利で絞ると候補が数点まで減るので、そのうち1点が自動で選ばれ、目で見る工程が飛んでいた。

対処は17.9と同じ二段構えだが、今回は**候補を一覧の1枚にして見る**ところまで道具にした
（`probe.py` で権利と寸法だけ先に並べ、`peek.py` で縮小版を落とし、`sheet.py` で1枚に並べる）。
7点の入れ替えで、見た候補は38点。**落とす前に見る**ほうが、落としてから気づくより速い。

### 19.3 検索よりカテゴリのほうが見つかる

`国会議事堂 昼間` のような検索語では、権利の通るものが出てこなかった。
`Category:National Diet Building` をたどると216件あり、そのうち権利の通るものが38件、
その中に `National Diet Building(in 2025).jpg`（Public domain・昼間の正面）と
`The Assembly Hall of National Diet.jpg`（衆議院本会議場）があった。
**検索は語の一致で切るが、カテゴリは人が集めた全部を見せる。** 権利で絞る前提なら、母数の大きいほうが当たる。

### 19.4 写せないものは、写せる別のもので代える

「日本銀行の円の形」は上空からしか見えず、俯瞰写真は CC BY-SA しかない。
最高裁の外観も、権利の通るものは擁壁ごしのものだけだった。
18.1 の「権利が通らないなら載せない」をそのまま当てると、どちらも写真なしになる。
今回は**別の角度から同じことを示す**ことにした。日銀は本館の全景を出して「上から見ると円の字」と説明に書き、
最高裁は外観をやめて**大法廷**（Public domain）にした。
最高裁は結果として、建物を見せるより「15人の裁判官が並ぶ法廷」を見せるほうが、単元の中身にも合っていた。
**権利で詰まったときは、同じ題材の別の面を探すと、かえって良くなることがある。**

## 20. 語彙の分野を足して分かったこと（2026-10-22 追記）

### 20.1 1500語は「1500の別々の語」にならない

英検2級の単語1500語を、15単元に100語ずつ割り振って書いた。
書き終えて数えたら、単元をまたいで同じ語が何度も出ていた。
improve、increase、provide のような、どの場面にも出てくる語である。

単語帳として出す以上、1500語は1500の別々の語でなければ数が意味を持たない。
そこで**ビルダーに重複の見張りを入れ**、あとに出たほうを機械で落として、
不足した数だけ書き足す、というくりかえしにした。
最初から入れておけばよかった。**数を売りにするデータは、数が本当かを機械で確かめる。**

漢検2級の1500語でも同じことが起き、こちらは最初から見張りを入れてあったので、
書いたそばから「k09 と k12 に重複」と出て、その場で直せた。手間がまるで違った。

### 20.2 題材が増えるほど、衝突しにくい語を選ぶようになる

単元が進むにつれて、重複の数が減っていった。
1〜5単元目は一度に19件も出たのに、7単元目以降はほとんど出ない。
これは慣れたからではなく、**書く前に「もう使った一般語」を一覧で見るようにしたから**である。

衝突するのは決まって、動詞・形容詞・副詞の一般語だった。
名詞は分野ごとに固有なので、ほとんどぶつからない。
だから一般語だけを並べた一覧を手元に置いて、それを避けながら書いた。
**全部を覚えておこうとせず、ぶつかる所だけを見る。**

### 20.3 単語帳は、既存の一覧タブに一行足すだけで作れた

「意味をかくす」機能は、新しい画面を作らずに済んだ。
一覧タブ（年表・統計・単語を並べるタブ）は、もともと全単元の `events` を縦に並べている。
ここに、説明の要素へ class を一つ足すだけで単語帳になる。

```js
const mask = CARD_MODE && S.set.mask ? ' masked' : '';
```

隠し方は CSS に任せた。`background` を文字色と同じにして `color: transparent` にすると、
帯で塗りつぶしたように見える。おすと `open` が付いて元に戻る。

**既存の画面に意味を一つ足すほうが、新しい画面を足すより安い。**
17.6（既定の動作を `APP` に出す）と同じで、分野ごとの違いは `APP.cardMode` の一つに寄せた。
立てていない18分野では、ボタンそのものが作られないので何も変わらない。

### 20.4 生成スクリプトは版を 1 に戻す

漢検2級に単語帳を入れるため `gen.py` で作り直したら、
`sw.js` の `CACHE` が `kanken2-v3` から `kanken2-v1` に戻っていた。
雛形には `-v1` と書いてあるので当然だが、**使っている分野を作り直すと版が巻き戻る**。

利用者の端末には v3 のキャッシュが残っているので、v1 を配ると古いほうが使われ続ける。
気づかなければ「直したのに反映されない」という、いちばん分かりにくい不具合になっていた。
作り直したあとに v4 へ直し、`tools/check/ver.js` で確かめた。

**検証を先に作っておくと、こういう巻き戻りがその場で止まる。**
16.2 で `ver.js` を足しておいたことが、ここで効いた。

### 20.5 クイズは語彙データから作れる

180問を手で書くつもりだったが、語義を問う形式（正誤判定・組合せ・短文）は
語彙データからそのまま作れることに気づいた。
まぎらわしい選択肢は、**同じ単元の同じ品詞の語**から選ぶ。そうすると、
「名詞の中から選ぶ」形になって、品詞で答えが割れない問題になる。

手で書いたのは程度配列だけである。これは並び順そのものが問題なので、
機械では作れない。単元ごとに三つ組を二つ、合わせて30組を用意した。

正解の位置は、順ぐりに割り当てて散らした（`sel` 26%、`cmb` 27%、`ord` 17%、`src` 27%）。
2.8 で苦労した偏りが、生成にすれば最初から起きない。
**手で書くと偏り、機械で作ると偏らない。** どちらで作るかは、偏りの直しやすさでも決まる。

## 21. 増やしたのに、アプリが古い数を名乗り続けていた（2026-10-22 追記）

### 21.1 症状は「プッシュされていない」という報告だった

漢検2級に、よく間違える常用漢字の語1500を足した。
データは1685件（配当漢字185＋1500）になり、コミットもプッシュも公開も済んでいた。
それでも「漢検2級の語彙が185だけど、プッシュされてない」と言われた。

調べると、一覧タブの件数は公開サイトでもちゃんと「1685件」と出ていた。
プッシュされていないものは一つもなかった。
では何が185だったかというと、**アプリが自分を説明している文のほうである**。

- `index.html` の `meta description`「配当漢字185字を…学べるアプリ」
- `manifest.webmanifest` の `description`（同じ文）
- テーマ別の前書き「185字はばらばらに見えるが…」
- トピックの本文「185字のうち、成り立ちをたどれるものは…」（計4か所）

数を足す作業は `data-units.js` の中だけで完結する。
だから、**その外側にある「自分は何者か」という文は、手がまったく触れない。**

### 21.2 数字より、散文のほうが強く読まれる

画面には「1685件」と出ていた。それでも185だと読まれた。
件数は小さな字で一行、散文は大きな字で何段落もある。
読む側は、先に目に入って意味のわかるほうを信じる。

**数は小さく、言葉は大きい。**
カウンタを正しくするだけでは、増えたことは伝わらない。

対処として、漢字タブの先頭に内訳を一行置いた。

```html
<p class="lead">配当漢字185字と、よく間違える常用漢字の語1500を合わせた1685件です。…</p>
```

あわせて、本文に裸で出てくる「185字」を「配当漢字185字」に直した。
全体の数と読めてしまう書き方が、そもそもの誤解のもとだったからである。
数が何の数かを書いておけば、あとで足しても嘘にならない。

### 21.3 増やしたら、増える前の数で grep する

点検はひどく簡単だった。`grep -rn "185"` を分野のフォルダにかけるだけで、
散文の5か所と meta の2か所が、そのまま並んで出てきた。

**数を足したときは、足す前の数で検索する。** これが一番安い点検である。
`tools/check` は件数の整合は見るが、散文が現物と合っているかは見ない。
15章でドキュメントについて同じことを書いたが、これはその**アプリ内版**だった。
ドキュメントだけでなく、アプリ自身も現物に追いつかなくなる。

機械にやらせるなら、「分野の総件数と違う3桁以上の数が散文にあれば挙げる」
くらいの検査になるが、正しい部分集合（配当漢字185字）まで挙がってしまう。
数のそばに何の数かが書いてあるかを見るほうが実効があり、それは人がやるしかない。

### 21.4 直すついでに版を上げる

説明文を直したので、`kanken2-v4` を `v5` に上げた。
文言だけの修正でも、利用者の端末には古い一式がキャッシュされている。
20.4 で版の巻き戻りに痛い目を見た直後だったので、今度は忘れずに上げられた。

**直したものが相手に届くところまでが修正である。** 直した時点では半分しか終わっていない。
